# Approach, Tools, and Assumptions

## The real assignment: requirements were in the interviews

The stakeholder notes are narrative on purpose. Everything built here traces to a person:

| Requirement | Who asked | How it shipped |
|---|---|---|
| Match brand / ABV / warning against application | Sarah | `app/checks.py` per-field checks |
| Results in ≤ 5 s | Sarah ("nobody's going to use it") | Local OCR path; **measured 0.22 s** end-to-end in the container, ~2 s worst case in tests |
| A 73-year-old can use it | Sarah | One screen, three inputs, one large button; no jargon |
| Batch uploads of 200–300 | Sarah / Janet | `/batch`: CSV + multi-image, filename↔row matching, problems sorted first |
| Warning must be exact, caps enforced | Jenny + 27 CFR 16.21/16.22 | Verbatim §16.21 constant; distinct REVIEW verdict for the title-case violation Jenny described |
| "STONE'S THROW" ≠ hard mismatch | Dave | Whole-word/fuzzy brand matching; case-only differences MATCH with a note |
| No cloud ML calls (firewall) | Marcus | Tesseract + OpenCV local; AI assist strictly opt-in and absent without a key |
| Standalone, no COLA, store nothing | Marcus | No database, no persistence, no auth surface |
| Imperfect photos | Jenny (stretch) | Otsu thresholding, denoise, upscale; Claude vision fallback for near-empty OCR |
| Tool advises, agent decides | Dave | No auto-reject exists: any finding → NEEDS REVIEW |

## Architecture

FastAPI, server-rendered. One pure-logic module (`checks.py` — zero I/O, 20 unit tests),
one OCR module, one optional AI module, one web layer. The 5-second requirement and the
firewall requirement point at the same design: **local-first**. Cloud vision would be more
accurate on bad photos but fails both constraints, which is exactly the trade the scanning
vendor lost in Sarah's pilot.

Verdicts are deliberately three-state per field (MATCH / REVIEW / MISMATCH, plus MISSING).
REVIEW exists because Dave is right: "technically a mismatch" is not a rejection. The
title-case warning, the near-miss brand — those go to a human with the evidence shown.

## What OCR cannot verify (stated, not hidden)

27 CFR §16.22 requires "GOVERNMENT WARNING" in **bold**, minimum type sizes in
millimeters, and a contrasting background. None of these are measurable from an
uncontrolled photo. The app verifies text content and capitalization deterministically
and reports the rest as requiring visual confirmation — it never claims a check it
cannot perform.

## Assumptions

- Sample labels are synthetic (generated by `scripts/make_samples.py`) — no real COLA
  data was available or used.
- Batch matching is by filename stem == `application_id`; a real integration would key
  on COLA IDs.
- English-language labels; single label per image.
- No authentication or persistence — prototype scope per Marcus ("don't do anything
  crazy... not storing anything sensitive").

## Path to production

- **Azure:** Treasury runs Azure (per Marcus). The container deploys unchanged to Azure
  Container Apps: `az containerapp up --name ttb-label-check --source .` — same image,
  no cloud dependencies inside, so it runs identically behind the agency firewall.
- **FedRAMP posture:** all processing in-boundary by default; the only optional egress
  (AI assist) is a single documented endpoint that can remain disabled.
- **COLA integration:** out of scope by instruction; the natural seam is `_run_one()`
  which takes application data + image bytes and returns a structured result.

## Tools used

AI-assisted development (Anthropic Claude via Claude Code) under human direction:
requirement extraction, TDD implementation (31 tests written before or alongside code),
regulatory verification against the live eCFR, and documentation. Runtime tooling:
Tesseract, OpenCV, rapidfuzz, FastAPI; optional Claude vision (disclosed in README).
